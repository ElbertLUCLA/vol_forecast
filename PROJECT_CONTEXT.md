## 1. Research question

**Which volatility model gives the best early warning of a large market drawdown?**

Five models (plus an LSTM control) are compared on SPY realized variance around two drawdowns of different character:

| Event key | Character | Market peak | Trough | Approx. S&P 500 decline |
|---|---|---|---|---|
| `covid` | Fast, sudden crash | 2020-02-19 | 2020-03-23 | ≈ −34% |
| `bear2022` | Slow, drawn-out decline | 2022-01-03 | 2022-10-12 | ≈ −25% |

Each model is trained only on data available **before** the run-up to the event, its parameters are frozen, and it then forecasts day by day through the run-up, the drawdown and the recovery. The question is how early and how strongly each model's variance forecast rises, measured fairly (a model that always forecasts high variance must not "win"; see §8).

**Sub-questions the design supports**

1. Does non-linearity (XGBoost trees, HARNet, Mamba) give earlier or stronger warnings than linear models (HAR, Linear-XGB), even if average accuracy at 1-week/1-month horizons is similar? (Teller et al. 2022 found non-linearity helps mainly at h = 1.)
2. Does downside information (negative semivariance, signed jumps: the `ext` feature set) raise forecasts earlier than RV alone (`base`)?
3. Do bounded model structures (tree ensembles; sequence models whose last layer is normalized or tanh-squashed) under-forecast during spikes because they cannot extrapolate beyond the training range?
4. Does the answer differ between a sudden crash (COVID) and a slow bear market (2022)?
5. How does a returns-only model (GARCH) compare with realized-variance models as a warning signal?

### 4.2 Pipeline stages (as implemented)

|---|---|---|

### 4.4 Feature store (`data/processed/spy_features.parquet`, 5,720 × 37)

**Conventions**

- One row per trading day *t*. **Features use information up to the close of day t; targets start at t+1.**
- Units are **daily decimal variance** (not percent, not annualized). Annualized volatility in % = √(252 · RV) · 100.
- "t + h" means h rows ahead in the feature store, i.e. h trading days (the two dropped sessions are simply skipped).
- RV covers regular trading hours only (09:30–16:00 ET); close-to-close returns include the overnight gap.

**Columns**

| Group | Columns |
|---|---|
| Raw measures | `rv`, `rs_pos`, `rs_neg`, `delta_j2`, `bpv`, `medrv`, `oc_return`, `rth_last_close`, `max_abs_5min_return` |
| Quality flags | `n_bars_observed`, `n_missing`, `is_early_close`, `rth_vs_daily_close_abs_pct_diff` |
| Daily bars / returns | `daily_open`, `daily_close`, `ret_cc`, `ret_cc_pct` (×100, for `arch`), `ret_overnight` |
| Base features | `log_rv_d` = ln RV_t; `log_rv_w` = ln mean(RV_{t−4..t}); `log_rv_m` = ln mean(RV_{t−21..t}) |
| Extended features | `log_rs_neg`, `log_rs_pos`, `log_rs_neg_w`, `log_rs_neg_m`, `jump_pct` = ln(1 + ΔJ²_t / RV_t) (range in sample −1.73 to 0.61), `sj_raw` = ΔJ²_t |
| Robustness | `mom` = RV_w − RV_m, `log_medrv` |
| Multi-Transformer original inputs (no longer used) | `ret_cc`, `ret_cc_roll_std_5` (5-day rolling std of `ret_cc`) |
| Targets, h ∈ {1, 5, 22} | `rv_h{h}` = mean(RV_{t+1..t+h}); `y_h{h}` = ln `rv_h{h}` |

### 4.5 Feature sets (`adapters.FEATURE_SETS`, mirrored in `configs/xgb.yaml`)

| Name | Columns | Used by |
|---|---|---|
| `base` | `log_rv_d`, `log_rv_w`, `log_rv_m` | all RV models |
| `ext` | `base` + `log_rs_neg`, `log_rs_neg_w`, `log_rs_neg_m`, `jump_pct` | HAR, XGBoost (the log version of HARNet eq. 29) |
| `extended` | `ext` + `log_rs_pos` | legacy superset from `plan.md`; RS⁺ is redundant given RV and RS⁻ |
| `ext_x` | `ext` + `ret_cc`, `ret_overnight`, `mom` | XGBoost robustness only (CJX-style); `log_vix` is not available yet |
| `mt_original` | `ret_cc`, `ret_cc_roll_std_5` | unused since the Multi-Transformer was dropped; kept in the store |

`harnet_view` returns **raw daily series**, not these log features: `["rv"]` for base and `["rv", "rs_neg", "delta_j2"]` for the extended HARNet. The extended branch is keyed by the string `"extended"`, which is a naming inconsistency with `ext` (§10).

## 5. Experimental design

### 5.1 Splits (actual dates in `data/processed/splits/*.json`)

| | `covid` | `bear2022` |
|---|---|---|
| Train | 2004-01-02 → 2018-05-25 | 2004-01-02 → **2020-12-31** (includes COVID; changed 2026-10-08, §9d) |
| Validation | 2018-05-29 → 2019-12-31 (last 10% of pre-cutoff days) | **2021-01-04 → 2021-09-30** (explicit `val_window` in `config.yaml`; was 2019-12-23 → 2021-09-30, which contained COVID) |
| Cutoff (= `train_end` = val end; parameters frozen here) | 2019-12-31 | 2021-09-30 |
| Pre-event (out-of-sample) | 2020-01-02 → 2020-02-19 | 2021-10-01 → 2022-01-03 |
| Event | 2020-02-20 → 2020-03-23 | 2022-01-04 → 2022-10-12 |
| Post-event | 2020-03-24 → 2020-06-30 | 2022-10-13 → 2023-03-31 |
| **Calm** (out-of-sample false-alarm reference) | 2020-07-01 → 2021-09-30 (ann. vol 11.9%) | 2023-04-03 → 2025-03-31 (10.0%) |

### 5.2 Rules that apply to every model

1. **Purging.** Any training/validation row whose target window [t+1, t+h] crosses a block boundary is dropped. The split files store the purged ends per horizon (`end_by_horizon`); `models/xgb/data.py::purge` reproduces them and asserts agreement.
2. **Frozen parameters, live inputs.** After the cutoff no model is refit. Each day's forecast uses that day's actual features (known at the close). This differs from the Multi-Transformer paper, which refits daily on a rolling window (§6.5).
3. **Refit before freezing.** Hyperparameters are chosen on the validation block, then the model is refit on train + val (all purged pre-cutoff rows). This differs from Teller et al., who kept the train-only model. Without it, the 2022 models would never be trained on COVID.
4. **Any scaler is fit on training data only** and saved with the model.
5. **Direct multi-step forecasting.** One model per horizon h ∈ {1, 5, 22}, target = mean RV over t+1..t+h. h = 5 and h = 22 are the headline horizons for early warning; h = 1 is kept for comparability with the literature.
6. **Log back-transform.** Models trained on log RV store `forecast_var = exp(ŷ) · S`, with S the Duan (1983) smearing factor from validation residuals of the train-only model. `forecast_var_naive = exp(ŷ)` is kept too. Models trained on the variance level (HARNet, GARCH) need no smearing.
7. **In-sample tail.** The last 63 pre-cutoff days are also forecast (`sample = "train_tail"`) so the evaluation can compute each model's warning *lift* relative to its own recent forecast level.

### 5.3 Shared forecast schema

`data/processed/forecasts/{event}/{model_name}.parquet`, one row per forecast-origin date (implemented in `models/schema.py::FORECAST_SCHEMA`):

`date, target_start, target_end, h, forecast_log, forecast_var, forecast_var_naive, forecast_var_seed_min, forecast_var_seed_max, realized_var, realized_log, target_complete, sample, model, booster, featureset, event`

- `sample` ∈ {`train_tail`, `pre_event`, `event`, `post_event`, `calm`}.
- `realized_var` is NaN (and `target_complete = False`) when t+h is past the end of the store.
- Every model writes this schema (`booster` = `gbtree`/`gblinear`/`ols`/`garch11t`/`HARNet20`/`HARNetSVJ20`/`lstm`/`mamba`; seed min/max NaN when not applicable), and `schema.validate_forecasts` checks it.

## 6. Models

### 6.1 GARCH baseline (built)

**References.** Engle (1982), ARCH (`Engle1982.pdf`); Bollerslev (1986), GARCH. Library: `arch` (Sheppard).

**Role.** Returns-only baseline that is common in practice. It uses no realized-variance features and has no feature-set dimension.

**Specification for this study**

| Item | Choice | Note |
|---|---|---|
| Model | GARCH(1,1), constant mean | `arch_model(ret_cc_pct, mean="Constant", vol="GARCH", p=1, q=1)` |
| Innovations | Student-t | matches the GARCH benchmarks in Ramos-Pérez et al. (2021) |
| Input | `ret_cc_pct` (close-to-close log return × 100) from `garch_view` | `arch` is numerically happier in percent |
| Fit window | train start → cutoff | single fit, frozen |
| Forecast | for each day t after the cutoff, filter the conditional variance with fixed parameters through t, forecast 1..h steps ahead, average to the mean daily variance over t+1..t+h | e.g. fix the fitted parameters on the full return series and use `forecast(horizon=22, start=...)` |
| Units | divide %² by 10⁴ to get decimal variance | |
| Grid | 2 events × 3 horizons = 6 forecast files | |

**Scale mismatch.** GARCH models close-to-close variance (including the overnight gap); RV is 09:30–16:00 only. Options recorded in `plan.md`: (a) multiply by a scaling factor estimated on training data, c = mean(RV)/mean(σ̂²_GARCH); (b) rely on rank-based or QLIKE comparisons. Store both the raw and the scaled forecast. Optional robustness: GJR-GARCH (leverage) via `o=1`.

**Implementation.** `models/garch/run_all.py`: `forecast_var` = c · GARCH variance (c ≈ 0.57 in both events, i.e. RTH variance is ~57% of close-to-close); `forecast_var_naive` = unscaled GARCH variance. Lift is unaffected by c. Validation metrics come from a separate train-only fit. Fitted persistence α+β ≈ 0.993, Student-t ν ≈ 5.4.

### 6.2 HAR (built)

**References.** Corsi (2009), HAR-RV; Patton & Sheppard (2015), semivariance and signed-jump extensions; log-HAR as in Teller et al. (2022, §3.1).

**Specification**

| Item | Choice |
|---|---|

### 6.4 HARNet (built: PyTorch port)

**Reference.** Reisenhofer, Bayer & Hautsch (2022), *HARNet: A Convolutional Neural Network for Realized Volatility Forecasting*, arXiv:2205.07719 (`harnet.pdf`). Reference code: `HARNet/src/harnet/` (TensorFlow, `model.py`, `main.py`, `util.py`; configs in `HARNet/configs/`).

**Architecture (from the paper §4 and `model.py`)**

- A hierarchy of **dilated causal 1-D convolutions** that generalizes HAR's averages. For aggregation periods (j₁, …, j_L) = (1, 5, 20) (`HARNet20`) or (1, 5, 20, 40, 80) (`HARNet80`):
  - layer 1: kernel size j₂ = 5, no dilation, initialized to 1/5 (a 5-day average)
  - layer l ≥ 2: kernel size j_{l+1}/j_l, dilation j_l, initialized to j_l/j_{l+1} (averaging the previous layer's averages)
  - **each period must be a multiple of the previous one** (the code raises otherwise), so **HARNet uses 20, not 22**, for its monthly component
- ReLU activation, no bias in the conv layers (`use_bias_dconv=False`), `filters_dconv = 1` (`2` in the extended HARNetSVJ).
- Output: a bias-free `Dense(1)` over [1, RV_t, avg₅, avg₂₀, …], **initialized with the OLS coefficients of the matching HAR baseline**, so before training HARNet reproduces that HAR exactly (with ReLU and non-negative inputs).
- Predictions are clipped below at the scaled value of **half the smallest training RV** and above at 1000 (scaled units).
- Receptive field = largest period (20 or 80 days), so the first 20/80 days are burn-in.

**Extended version (HARNetSVJ, paper §6, eq. 29).** Input channels [RV, RS⁻, ΔJ²]. The conv layers average RV and RS⁻ (two filters, initialized as separate averages); ΔJ² enters only the output layer as a daily value. The output layer is initialized from the OLS fit of
RV_t = β₀ + β₁RV_{t−1} + β₂RV^(5)_{t−1} + β₃RV^(20)_{t−1} + β₄RS⁻_{t−1} + β₅RS⁻^(5)_{t−1} + β₆RS⁻^(20)_{t−1} + β₇ΔJ²_{t−1}.
For log variants, ΔJ² is replaced by 1 + ΔJ²/RV before taking logs, which is exactly the store's `jump_pct`. `adapters.harnet_view(..., "extended")` already returns `[rv, rs_neg, delta_j2]` in the reference's channel order.

**Training settings (paper Table 1 and §5; `util.py::HARNetCfg`)**

| Item | Paper / reference value |
|---|---|
| Optimizer | Adam, fixed learning rate 1e-4 |
| Iterations | 10,000 (`epochs=10000`, `steps_per_epoch=1`) |
| Batch size | 4 random windows |
| Labels per window | 5 consecutive one-day-ahead labels (`label_length=5`), so 20 labels per batch |
| Loss | QLIKE (**recommended**); MSE and MAE also tested |
| Baseline fit for initialization | OLS (**recommended**); WLS and log-OLS also tested |
| Input scaling | fixed linear map: 0 → 0 and 1e-3 → 1 (`MinMax(0, 0.001)`); for log variants −13 → 0 and −2.5 → 1 (code configs use −17) |
| Train/test design | 15 rolling pairs: 4 years train (~1,000 labels, ≈ 200 epochs) → next year test; SPX, FTSE, DJI from the Oxford-Man library, 2001-08 → 2020-12 |
| Best-weights option | `save_best_weights` keeps the weights with the best value of a chosen metric |

Paper conclusion (§5.3): **QLIKE loss + OLS initialization** is the most reliable combination. Log-OLS initialization barely changes the baseline, and WLS often hurts. HARNet20 is more stable than HARNet80 in the extended setting.

**Adaptations this study needs**

| Issue | Reference behaviour | Needed here |
|---|---|---|
| Horizon | One-day-ahead only: labels are the input RV channel itself (`labels_from_inp_ts`) | Direct h ∈ {1, 5, 22}: labels = `rv_h{h}` (mean forward RV), baseline HAR fit by OLS on that same target, output layer initialized from it |
| Target scale | RV level, QLIKE loss | Keep levels (no smearing needed); forecasts go straight into `forecast_var` |
| Training sample | 4-year rolling window | Full pre-cutoff sample (consistent with the other models). At ~4,000 labels, 10,000 iterations is only ≈ 50 epochs, so the iteration count, or validation-based best-weights selection, needs revisiting. A 4-year window is a natural robustness check. |
| Splits | Calendar years | Event splits with purging (§5); validation block used for best-weights/early stopping, then refit or keep (decide, §10) |
| Scaler | Fixed constants (not fit to data), no leakage | Same constants are fine. SPY RV in COVID reaches ≈ 0.006, i.e. 6 in scaled units; the clip at 1000 is far away. |
| Seeds | Random batches, no seed ensemble | Seed ensemble (e.g. 5 seeds, as XGBoost) with min/max band |
| Monthly period | 20 days | Keep 20 (architectural constraint) and document the 22-vs-20 difference from HAR/XGBoost |
| Framework | TF ≥ 2.5, `pydantic` dataclass config, old `tensorflow.python.keras` imports, `optimizer.lr` | Likely breaks on current TF/Keras 3; a small PyTorch port is an option (the model is ~3 conv layers + a linear layer) |

**Grid.** 2 events × {base (`HARNet20`), ext (`HARNetSVJ20`)} × 3 horizons = 12 cells; `HARNet80` optional (set `lags: [1, 5, 20, 40, 80]`).

**Implementation (`src/volforecast/models/harnet/`).**

- `model.py::HARNetEnsemble` ports `HARNet`/`HARNetSVJ`. Every parameter has a leading seed dimension, so the 5 seed copies train as one vectorized model. The loss is summed over seeds and Adam is elementwise, so each copy trains exactly as it would alone (tested).
- Float64 throughout. At initialization the network reproduces the OLS HAR to ~1e-16 (tested for HARNet20/80, base/ext).
- `data.py` reuses `xgb.data.build_frames` for segment membership and purging, so HARNet labels sit on exactly the XGBoost rows, checked against `end_by_horizon`. The input is the full raw series (`rv`, plus `rs_neg` and `delta_j2` for ext), scaled by the paper's fixed map x/1e-3.
- Labels are the direct targets `rv_h{h}`; the OLS baseline is fit on the same target (decision #3).
- `train.py`, following the paper: Adam with lr 1e-4, QLIKE, batches of 4 windows × 5 consecutive labels, clipping at [½·min training RV, 1000].
- Iteration count: up to 40,000 iterations, evaluating seed-averaged validation QLIKE every 250. Iteration 0 is the OLS-initialized HAR, so HARNet only departs from HAR when that helps on validation. Training stops after 40 evaluations without improvement. The best iteration count is then used to refit on train + val from a fresh OLS init (decision #4, the same refit logic as XGBoost).
- Outputs:
  - forecasts in the shared schema (`booster` = `HARNet20`/`HARNetSVJ20`; `forecast_var = forecast_var_naive`, no smearing; seed min/max band)
  - `weights.pt` with a SHA-256 hash re-verified after forecasting
  - `params.json` (both OLS fits, best_iter)
  - `val_curve.csv`
  - `diagnostics.json` with validation QLIKE/MSE for HARNet, its HAR initialization and the random walk

### 6.5 Mamba (replaces the Multi-Transformer) and an LSTM control

**Why the switch (decided 2026-10-05).** The Multi-Transformer reference is TF/Keras notebooks, and its design differs from this study on almost every axis: it predicts a 5-day return std, takes GARCH outputs as inputs, refits daily on 650 days, and has a sigmoid head. Porting it would have produced a loosely related model at high tuning risk. Teller et al. already report LSTM as weak, so the deep-learning question this thesis asks instead is: **does an enhanced long-memory recurrent architecture help?** The answer comes from Mamba, a selective state-space model (Gu & Dao 2023), compared against plain recurrence (LSTM, Hochreiter & Schmidhuber 1997) on identical inputs. The Multi-Transformer reference repo was removed.

**Design (`src/volforecast/models/seq/`, `configs/seq.yaml`)**

| Item | Choice |
|---|---|
| Inputs | **Raw daily series only**: `base` = [`log_rv_d`]; `ext` = [`log_rv_d`, `log_rs_neg`, `jump_pct`]. No precomputed weekly/monthly averages, so the network must learn its own memory, the same principle as HARNet. Standardized with training-block mean/std. |
| Lookback | tuned per cell on validation from {22, 66, 126} days. 126 ≈ 6 months, far beyond HAR's 22 and HARNet's 20 |
| Architecture | `Linear(C → 16)` → backbone (2 layers, hidden 16) → last step → `Linear(16 → 1)`. Mamba: `transformers.MambaModel` (state 16, expand 2, conv 4), ~7k parameters. LSTM: `nn.LSTM(C, 16, 2 layers)` |
| Target / loss | `y_h{h}` (log mean forward RV), MSE, then smearing, the same as HAR/XGBoost |
| Training | AdamW lr 2e-3, batch 256, grad clip 1, up to 150 epochs, early stopping (patience 15) on validation MSE |
| Seeds / refit | 5 seeds. Each seed's best epoch from the train-only fit, then a refit on train + val for that many epochs, frozen (weights hashed). S from the seed-averaged train-only validation residuals |
| Output ceiling | Mamba's last hidden state is RMS-normalized, so its output is ≤ b + √d·‖w∘g‖. LSTM's is < b + Σ\|w\| (tanh). Both are reported like the tree ceiling |
| Hardware | Mamba: AMD GPU via `.venv-rocm` (§3); LSTM: CPU (2 threads) |
| Grid | 2 events × {base, ext} × 3 horizons × {mamba, lstm} = 24 cells |

## 8. Evaluation framework (built: `src/volforecast/evaluation.py`, `notebooks/02_model_comparison.ipynb`)

All metrics are computed per event, per window (`pre_event`, `event`, `post_event`, `calm`) and per horizon, from the shared forecast files. Tables and figures go to `reports/eval/`.

1. **Accuracy.** Only QLIKE and variance-scale MSE rank forecasts correctly when RV is a noisy proxy for true variance (Patton 2011), and both score the smeared `forecast_var`.
   - **QLIKE** (`models/common.py::qlike`) is the **primary** metric. It penalizes under-prediction heavily, which suits a risk question.
   - **Variance-scale MSE** (`mse_var`) is the **secondary** metric, in (daily %²)², i.e. variance × 10⁴. No model trains on it, so it is the neutral second opinion. It also gets a DM table (`dm_vs_benchmark(loss="mse_var")`) and a ratio to HAR-base (`mse_var_rel`). Crash days dominate it, so it is reported per window and never pooled.
   - **Variance-scale MAE** (`mae_var`, daily %²) is there only for comparability with Teller et al. and Reisenhofer et al. It is not robust and not used for ranking.
   - **Log-scale MSE** (`mse_log`) is a diagnostic only. It is not robust, and it favours the log models: their unsmeared `forecast_log` ≈ E[ln RV], while HARNet's ln(forecast_var) sits above it.
2. **Early-warning lift.** forecast_var ÷ the long-run mean RV of the event's training sample ("normal", common to all models; default `basis="longrun"`). The originally planned baseline, the model's own mean `train_tail` forecast (`basis="tail"`), is kept as a secondary view because it is degenerate for 2022. Report the first date the ratio crosses fixed thresholds (e.g. 1.5×, 2×) and the lead time in trading days relative to the peak.
3. **Under-prediction at onset / continuation.** Over the first 10 event days: coverage = forecast ÷ realized (forward), escalation = forecast ÷ trailing 5-day RV (> 1 means the model expects worse to come), and cumulative shortfall. For 2022, tracking over the whole event window: QLIKE, mean ln(forecast/realized), share of days under-predicted.
4. **False alarms / alarm skill (decided).** alarm = lift ≥ τ, stress = realized lift ≥ τ (realized ÷ the same long-run normal), over all out-of-sample days including a **calm window** after each event (§5.1). Reported: hit rate, false-alarm rate, Peirce skill score (= hit − false alarm; an always-alarm model scores 0), alarm-to-stress ratio, and calm-window bias.
5. **Significance.** Diebold–Mariano tests on QLIKE and on variance-scale MSE vs HAR-base, with Newey–West variance (built). Model confidence set (Hansen, Lunde & Nason 2011; `arch.bootstrap.MCS`) is still optional.
6. **Optional VaR backtest.** 1-day VaR exceedances with Kupiec/Christoffersen tests (not built).

**Interpretation caveat.** For pre-event rows near the peak, the h = 22 target window already reaches into the event (e.g. a forecast made on 2020-02-10 targets mean RV through mid-March). "Realized" in the pre-event window is therefore partly event volatility at long horizons. Lead-time analysis should use the forecast series itself (lift and threshold crossings), not only forecast-vs-realized loss.

  - Every model over-forecasts in calm markets after a shock.

### 9d. Finding: an unseen crash in the validation block inflates the smearing factor (2022)

**What happened.** Log-target models (HAR, XGBoost, LSTM, Mamba) are converted back to variance with Duan's smearing factor S = mean(exp(validation residual)) of the *train-only* model. With the default rule (validation = last 10% of pre-cutoff days), the 2022 validation block was 2019-12-23 → 2021-09-30. **It contained the COVID crash, but the train-only models had been trained only through 2019-12.** They badly under-predicted March 2020, their validation residuals were huge, and S inflated. The refit models, which *were* trained on COVID, then inherited that S, so the COVID surprise was counted twice.

**Fix (adopted).** Train through 2020-12-31 (the crash is now in training) and validate on 2021-01-04 → 2021-09-30. The cutoff, refit sample and forecast period are unchanged. The old results are archived in `data/processed/archive/val_with_covid/`, and `evaluation.smearing_comparison` reproduces the comparison.

| 2022, `ext` set | S at h = 1 / 5 / 22, validation with COVID | S, post-COVID validation | Calm-window bias at h = 22 (log), old → new | Alarm-to-stress at h = 22 (2× normal), old → new |
|---|---|---|---|---|
| HAR | 1.29 / 1.41 / **2.30** | 1.23 / 1.20 / **1.06** | +0.79 → +0.02 | 3.00 → 0.21 |
| XGB-linear | 1.31 / 1.43 / **2.30** | 1.23 / 1.11 / **0.96** | +0.85 → −0.00 | 2.71 → 0.00 |
| XGB-tree | 1.29 / 1.38 / **2.21** | 1.20 / 1.11 / **1.01** | +0.80 → −0.02 | 2.46 → 0.02 |
| LSTM | 1.31 / 1.39 / **2.25** | 1.29 / 1.24 / **1.05** | +0.76 → −0.07 | 2.89 → 0.01 |
| Mamba | 1.32 / 1.41 / **2.09** | pending GPU re-run | +0.75 → pending | 2.16 → pending |

HARNet and GARCH (level models) have no S. Their 2022 results changed only through re-tuning on the new validation block.

**Why it matters for the thesis.**
1. With the inflated S, the 2022 log models appeared to "warn" in October 2021 and to track the bear market best. That was largely a uniform ~2.2× over-forecast: QLIKE penalizes under-prediction more than over-prediction, so an inflated forecast scores well in a high-volatility period, yet it over-forecasts a calm market by the same factor. Corrected, these models over-forecast calm markets by ~0, and at h = 22 they almost stop raising alarms during 2022.
2. **General lesson:** a retransformation correction estimated out of sample is only valid when the validation block resembles what the frozen model has learned. A regime shift the model never saw, *inside* the validation block, contaminates every forecast through S. Rolling or expanding validation that includes the shock in training is the remedy.
3. **Rejected alternative:** validating on post-2023 data. It would use information from after the forecast period (look-ahead), and it overlaps the calm window used to measure false alarms (circular).
4. **Consequence: the 2022 ranking reverses at h = 22.** Mean event-window forecast against 19.1% realized vol:
   - HARNet 18.5% (QLIKE 0.169) and GARCH 18.4% (0.175) track best.
   - The log models stay near normal: HAR 16.7%, XGB-tree 15.1%, LSTM 14.8%, XGB-linear 13.9% (log bias −0.26 to −0.60). XGBoost and LSTM are significantly worse than HAR (DM p ≤ 0.038).

   Under the old split the same log models looked best (XGB-tree QLIKE 0.11). Similar QLIKE can come from opposite errors: HAR scores 0.19 with bias +0.52 under the old split and 0.20 with bias −0.26 under the new one.
5. **Caveat of the fix:** the new validation block (2021) is calm (10.3% vol), so tuning favors models that expect calm. Report both splits (`reports/eval/smearing_finding_2022.csv`, notebook §7). With COVID in training, the 2022 LSTM picks a 126-day lookback in 4 of 6 cells, against 22 days before.

## 11. Glossary

| Term | Meaning here |
|---|---|
| RV | Realized variance: sum of squared 5-min RTH log returns, daily decimal variance |
| RS⁺ / RS⁻ | Positive / negative realized semivariance |
| ΔJ² | Signed jump variation, RS⁺ − RS⁻ |
| `jump_pct` | ln(1 + ΔJ²/RV), log-safe signed jump (Patton & Sheppard 2015) |
| Cutoff | Last day of training + validation; parameters frozen after it |
| Purge | Dropping rows whose h-day target window crosses a block boundary |
| Smearing (S) | Duan (1983) factor mean(exp(residual)) to undo log-retransformation bias |
| Ceiling | Largest value a tree ensemble can output |
| Cell | One (event, feature set, horizon, variant) model fit |
| Lift | Forecast ÷ the long-run mean RV of the training sample ("normal"); the own-train-tail baseline is a secondary view |

## 13. Task: add variance-scale MSE (and MAE) to the evaluation (added 2026-10-08)

**Status: done 2026-10-08.** `accuracy_table` (`mse_var`, `mae_var`, `mse_var_rel`), `tracking_table` (`mse_var`), `dm_vs_benchmark(loss=...)`, `tests/test_evaluation.py`, notebook §2/§4/§5 rebuilt and re-executed (Mamba 2022 rows included). `dm_test` now returns (0, 1) when the loss differential is identically zero. Outputs: `reports/eval/accuracy_by_window.csv`, `dm_event_vs_har_mse_var.csv`.

**Why.** Patton (2011, Prop. 2 and Table 1) shows that only two common losses rank forecasts correctly when RV is used as a noisy proxy for true variance: QLIKE and MSE on the variance scale. §8 lists variance-scale MSE, but `evaluation.py` never computes it. `accuracy_table` currently reports QLIKE, log-scale MSE (`mse_log`) and log bias only. The thesis will report:

| Loss | Role in the thesis |
|---|---|
| QLIKE | Primary metric (unchanged) |
| MSE, variance scale | **Secondary metric (to add)**: robust, and it is no model's training loss, so it is the neutral second opinion |
| MAE, variance scale | **To add**, for comparability with Teller et al. and Reisenhofer et al. only (not robust, not used for ranking) |
| MSE, log scale | Keep, but as a diagnostic only. It is not robust, and it favours the log models: their `forecast_log` is the unsmeared ŷ ≈ E[ln RV], which is exactly what this loss rewards, while HARNet's `forecast_log` = ln(forecast_var) sits above E[ln RV] |

**No model needs to be re-trained or re-run.** Every forecast file (`data/processed/forecasts/{event}/{model}.parquet`) already holds `forecast_var` (smeared for log models, seed-averaged where applicable) and `realized_var`. The new losses are pure post-processing in `evaluation.py`. Saved model weights are not needed.

**Steps**

1. **Helpers in `src/volforecast/evaluation.py`**, next to `_qlike`:

   def _se_var(r, f):
       return ((r - f) * VAR_SCALE) ** 2

   def _ae_var(r, f):
       return np.abs(r - f) * VAR_SCALE
